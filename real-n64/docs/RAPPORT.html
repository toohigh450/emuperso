Opération N64 Web — première exécution réelle

Résultat : une vraie ROM autonome démarre dans EmulatorJS / mupen64plus_next.

Code VR4300, vidéo VI, commandes SI et audio AI réellement exécutés. Sept groupes de tests passent dans Chromium/Linux. Aucun résultat sur le PC de Karl n’est prétendu.

Ce qui fonctionne, et quelle ROM

Le résultat positif concerne le port autonome situé dans homebrew/fallback-open/, et non le runtime libdragon de Claude. Il reprend compteur, carré animé, changement de couleur, A/B et tonalité, avec du code C freestanding et un bootstrap MIPS ouvert. Le JavaScript ne dessine pas le jeu et ne fabrique pas les échantillons audio de la ROM.

ROM : demo-emuperso-open.z64, 6 144 octets. SHA-256 : f18280a16c83721bdd56564701d505f96346784f36168402e5431b12499e2252. Les octets du fichier effectivement remis au cœur dans son système de fichiers émulé ont été rehashés et correspondent. Le linker n’utilise que les deux objets start.o et main.o : aucune bibliothèque SDK, Newlib ou libgcc dans ce port.

Ce bootstrap suppose 8 Mio de RAM alloués par l’émulateur. Il ne calibre pas la RDRAM physique et n’est pas validé sur console. Le cœur signale un CIC inconnu puis utilise sa voie 6102 ; aucun boot Nintendo commercial n’a été copié. Les CRC de header ne constituent pas une validation de console. Cette restriction est explicite dans les sources et le README.

Reprise du travail de Claude

La branche de base est emulateur-reel, commit 1219ecfeb51a43011c050b0113aa01dd5249ed9e. Les sources demo-n64/main.c, Makefile et LICENSE sont conservées byte pour byte ; leurs copies homebrew ont compilé sans correction C/Makefile. La ROM standard fait 147 456 octets, SHA dbcac8bbc7922f21844a298544cb65d26a1b33874be2f9652ebacee4f5c8e727.

ÉCHOUÉ : démarrage de cette ROM standard avec le cœur distribué testé. Le mode interpréteur avec cache a échoué à allouer sa mémoire puis a levé une erreur de table Wasm. Le mode interpréteur simple n’a pas donné d’image. Une variante IPL3 sans calibration a ensuite levé un accès mémoire Wasm hors limites ; un autre bootstrap CPU du programme SDK n’a pas montré de progression. Ces variantes ne sont pas déclarées fonctionnelles.

Les messages « IPL3 detected 64 MB » ne démontrent pas une mauvaise détection de RAM par libdragon : le cœur utilise une convention de registre du boot Nintendo qui ne s’applique pas nécessairement à l’IPL3 ouvert. La compatibilité de ce vieux cœur avec le libdragon moderne reste une limite, pas une cause unique complètement prouvée. Les sources officielles recommandent Ares pour la fidélité matérielle homebrew.

La solution retenue est un nouveau port libre dans ce projet, pas une ROM tierce commerciale ou un téléchargement de jeu. Aucun binaire tiers homebrew préexistant n’a été utilisé comme preuve. L’objectif pratique du premier démarrage est atteint par le port ; l’objectif de faire démarrer la ROM SDK originale reste ouvert.

Chaîne et versions vérifiées

  • SDK libdragon : e356bf3f56f7afbf7e5246329562f145965cfdfc.
  • Chaîne native officielle GCC 16.2.0, Newlib 4.4.0, paquet .deb SHA-256 fac8e6572493a66468b7d45df41b042f90b1a630ec96aa218bd5fb1f320a0a4d, extraite dans cache/ sans installation système.
  • Docker GHCR : accès refusé dans cet environnement, route non validée. La compilation réelle utilise la route native officielle.
  • EmulatorJS 4.2.3, commit frontend e150dc0491ae747028919fb82d6598954976ede6. Paquets NPM officiels 4.2.3 verrouillés par SHA-256 et SHA-512, sans npm install ni lifecycle.
  • Cœur explicite mupen64plus_next, métadonnées build 2.0.2, minimum EJS 4.2.2 ; interpréteur simple, WebGL2, threads désactivés. Le numéro de build ne démontre pas à lui seul un commit source exact du binaire.
  • 39 assets installés et vérifiés ; code frontend non minifié. La vérification publique des mises à jour est redirigée vers la version locale figée, et tous les fichiers du moteur sont servis localement au lancement testé.

La stabilité supplémentaire observée est de trente secondes, pas un test d’endurance. Les buffers audio natifs ordonnancés montrent RMS maximal 0,1361908 avec A et zéro avant/après. La première sonde AnalyserNode donnait zéro ; l’observation des buffers réellement programmés a démontré le signal sans modifier les données. Une sortie audible sur haut-parleurs n’est pas vérifiée dans le cloud.

Le parcours final n’a aucune erreur JavaScript de page, aucune erreur ou alerte console enregistrée. Les messages de debug/libretro restent dans les preuves. Cinq contrôles d’outillage passent : chemins, symlinks, hashes et préservation. L’installateur runtime passe en mode cache hors ligne et vérification seule ; ses téléchargements ont été réalisés séparément par Codex, le parcours réseau agrégé de l’installateur n’est pas prétendu testé depuis une machine vierge.

Protection des projets et GitHub

Seuls real-n64/ et le nouveau workflow .github/workflows/real-n64.yml sont ajoutés. Les 98 fichiers suivis à la base ont été comparés à leurs empreintes : inchangés, y compris le Lab et les sources de Claude. Aucune sauvegarde originale, ROM commerciale, Conker ou TN-1 n’a été utilisé. Le serveur est borné à 127.0.0.1 ; aucun endpoint n’écrit dans les projets. IndexedDB interne au moteur peut exister sous cette origine dédiée ; ce n’est pas une garantie RAM seulement.

Le premier lancement CI a révélé un faux refus de source SDK modifiée après clone sans checkout. Le bootstrap a été corrigé (initialisation vide, fetch du commit exact, checkout) et testé sur un dépôt local vierge avec conservation des modifications existantes. Le résultat du nouveau lancement CI reste distinct des tests locaux. Le workflow est filtré sur emulateur-reel et son job refuse toute autre ref. Il compile, vérifie les dépendances et prévoit le test réel ; aucun déploiement ni fusion. Les résultats CI sont séparés des résultats locaux : aucune réussite CI n’est déduite du seul fichier workflow. main n’est jamais une destination d’écriture.

Non testable et problèmes ouverts

  • Chrome Windows de Karl, son matériel, écoute des haut-parleurs et manette physique : NON TESTABLE ici.
  • Edge, Firefox, Safari, console N64 physique et autres ROM : non testés.
  • Endurance longue, récupération d’états réels, PAL et précision générale audio/vidéo : non validés.
  • ROM SDK standard et variantes expérimentales : compilation acquise, démarrage échoué/non démontré dans cette configuration.
  • Vitesse sur PC de Karl, Conker PAL et correction Sonic : aucune preuve et aucune revendication.
  • Une reprise sur une machine vierge et le workflow doivent être audités séparément. SHA-256 assure une concordance d’intégrité, pas une signature ou preuve d’auteur.

Mode d’emploi et remise aux auditeurs

Lire README-FR.md, exécuter python tools/fetch_runtime.py puis python tools/serve.py et ouvrir localhost:8770 dans Chrome. Le runtime demande Internet à la préparation, pas pendant le lancement testé. Le ZIP contient la ROM autonome compilée, sources, scripts, notices, preuves, manifeste et rapport ; les grandes dépendances vendor/cache sont exclues.

Pour GPT : vérifier d’abord les hashes de ROM et du FS émulé, la carte de liens, les sept résultats et la séparation des variantes échouées.
