N64 Web 0.4.0

Rapport pour Karl, GPT et Méo. Branche emulateur-reel uniquement. Application indépendante ; aucun fichier original du Lab, Conker, TN-1 ou de main modifié. Aucune ROM privée dans les sources, tests, archives ou artefacts.

Lancement inchangé : extraire l’application, double-cliquer DEMARRER-N64. Choisir une ROM brute ou un ZIP, puis lancer. Pendant une partie, choisir et lancer le prochain jeu sans fermer l’application.

Garde-fous techniques

Le frontend et le cœur restent les versions figées d’EmulatorJS 4.2.3 et mupen64plus_next distribué 2.0.2. Les fichiers tiers sont inchangés et vérifiables. L’adaptateur remplace le montage IDBFS automatique du cœur par une mémoire de session ; notre coffre effectue les écritures persistantes. L’iframe isole le cycle de vie, pas une frontière de sécurité face à du JavaScript de même origine.

Les chargements rapides, contextuels et par glisser-déposer du moteur sont bloqués pour éviter de contourner le coffre. Les paramètres du cœur sont fixes et liés à l’identité des états ; la configuration des manettes reste disponible. Le lancement de ROM et les commandes de session sont sérialisés ; les lectures concurrentes utilisent une génération et un signal d’annulation.

Le retour natif de load_state vaut 0 aussi bien pour un état valide que pour un fichier invalide sur ce build. Il n’est donc jamais présenté comme une preuve de réussite. Le coffre contrôle les SHA-256 et les identités ; le pont contrôle le conteneur RASTATE/Mupen, sa version et son identité ROM interne contre le cœur neuf, puis observe la progression. Les tests prouvent la restauration d’une mémoire connue et du PCM réel ; ils ne prouvent pas tous les états de tous les jeux.

La mémoire reste marquée après désactivation de cheats tant qu’elle peut contenir leurs effets. Une sauvegarde native identique à la copie d’avant cheats n’est pas déclarée altérée sur le seul fait d’avoir utilisé un code RAM. Un chargement d’état marqué demande confirmation.

Limites et problèmes ouverts

  • Aucune promesse de chargement sans bug sur tous les jeux, de correction Sonic ou de compatibilité commerciale. Le build du cœur reste ancien et sa provenance source exacte à établir avant redistribution de ses binaires.
  • Les codes communautaires ne sont pas tous compatibles, vérifiés ou sans effets indésirables ; le catalogue annonce une correspondance d’en-tête. Cruis’n USA PAL possède plusieurs variantes au même identifiant : choix requis.
  • La sauvegarde native réelle a été vérifiée avec une mutation contrôlée de notre fixture. Cela ne remplace pas une validation de progression commerciale, d’EEPROM/SRAM/Controller Pak sur plusieurs jeux ou d’une manette physique.
  • Effacement de données du navigateur, quota refusé ou arrêt brutal peuvent perdre les dernières modifications non enregistrées. Stockage persistant à demander et exports à conserver. Le coffre refuse d’écraser un contenu corrompu ; une copie précédente peut être chargée/exportée vers un autre emplacement.
  • État groupé ≤ 64 Mio, natif ≤ 1 Mio, import JSON ≤ 90 Mio. ROM ≤ 64 Mio, ZIP32 non chiffré ≤ 96 Mio ; limites ZIP de 0.3 conservées.
  • Dans cet environnement, un export après réouverture de profil ferme l’onglet avec Chromium 154 Linux sans interface, même sans moteur N64. Ce comportement n’est pas reproduit avec Chrome for Testing 151.0.7922.34 utilisé pour le parcours complet. Sa cause n’est pas établie ; Chrome Windows de Karl reste à valider.
  • Les anciens save states non enveloppés ne sont pas importés directement. Les réglages avancés du cœur restent verrouillés pour maintenir l’identité de configuration.
