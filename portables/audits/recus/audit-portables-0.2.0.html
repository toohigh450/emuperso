À vérifier

Les activations de codes que le moteur peut restaurer

Constat
La documentation précise que les nouveaux codes sont proposés désactivés, mais que le moteur peut restaurer une activation mémorisée. L'analyse indique avoir vérifié cela dans le code source d'EmulatorJS, sans dire comment la mémorisation est indexée.
Pourquoi
C'est le risque du « cheat fantôme » : un code activé dans un jeu qui se retrouve actif dans un autre, ou après un redémarrage, sans que l'interface le montre.
Action
Test réel : activer un code dans le jeu A, ouvrir le jeu B de la même console, puis relancer A. Dans chaque cas, comparer l'état du gestionnaire de codes à celui du jeu. Vérifier que TESTS-KARL.md couvre ce scénario (je ne l'ai pas lu).
À vérifier

La mémoire avec les grosses ROM DS

Constat
L'empreinte SHA-256 porte désormais sur tous les octets, même au-delà de 256 Mio. Le fichier est lu en entier, haché en entier, puis copié vers le moteur. La documentation reconnaît que ces copies peuvent s'additionner. L'API de hachage du navigateur n'offre pas de calcul progressif.
Pourquoi
Sur une ROM DS de 512 Mio, l'onglet peut planter sans message clair.
Action
Tester avec ta plus grosse ROM DS. Si l'onglet plante, soit un calcul progressif par morceaux, soit un message explicite au-dessus d'un seuil, plutôt qu'un plantage.
À vérifier

Le passage de 0.1 à 0.2 peut donner l'impression de perdre des sauvegardes

Constat
Pour les ROM DS de plus de 256 Mio, l'identifiant change entre les deux versions. La documentation demande d'exporter avant la mise à jour. Les jeux déjà connus gardent leur ancien nom interne, ce qui est la bonne approche pour les autres.
Action
Tester la mise à jour sur un profil Chrome qui contient des sauvegardes 0.1. Idéalement, afficher une bannière quand l'historique contient un jeu hors de la règle des noms conservés.
À vérifier

Le lanceur est identique à celui de la 0.1

Constat
Le fichier .bat n'a pas changé. Trois points : l'alias « python » du Microsoft Store peut être trouvé par where sans exécuter Python ; si le serveur de secours est arrêté avec Ctrl+C, le message « aucune solution de secours » peut s'afficher à tort ; et un fichier .bat aux fins de ligne LF (téléchargement du ZIP GitHub) est plus fragile qu'en CRLF.
Action
Tester le double-clic sur ton PC, en ZIP téléchargé et en clone. Envisager un .gitattributes qui impose CRLF aux .bat (décision à prendre, il sort de portables/).

Amélioration

Amélioration

Changer de jeu détruit l'ancien avant de savoir si le nouveau se charge

Constat
La description dit que l'échec de lecture d'une nouvelle ROM laisse le jeu précédent intact. Mais si le moteur ne se charge pas après la fermeture de l'ancien (Internet coupé en cours de session), la progression non enregistrée est perdue.
Action
Vérifier que le moteur est joignable avant de fermer l'ancien jeu, ou l'indiquer dans la boîte de confirmation.
Limite documentée

Une seule association manuelle de codes par ROM

Constat
Impossible de garder à la fois un fichier Code Breaker et un fichier GameShark pour une même ROM, sauf par la déclaration rom_sha256 dans les fichiers. Un fichier modifié au même chemin après l'association n'est pas détecté. Les deux limites sont écrites dans la documentation.
Action
Acceptable en l'état. À revoir si tu veux plusieurs formats par jeu.

Ce qui est solide

  • Périmètre respecté. La pull request affiche 35 fichiers, +3 042 lignes et 0 suppression, tous sous portables/. Elle est en brouillon, non fusionnée, et le texte dit que les branches N64 et PS1 ne sont pas touchées.
  • Aucune affirmation excessive. Le texte, ETAT.md et LISEZMOI.md répètent ce qui n'est pas validé. Aucune compatibilité universelle n'est revendiquée. Aucune ROM, aucun BIOS, aucune base de codes n'est ajouté.
  • Les codes ne sont plus liés au nom du fichier. Le nom devient une suggestion, l'association confirmée est liée à l'empreinte complète de la ROM, et une déclaration rom_sha256 dans un .cht permet une correspondance automatique. La documentation précise qu'une empreinte ne prouve pas l'efficacité d'un code.
  • Traçabilité. Les empreintes SHA-256 des archives 0.1.0 et 0.2.0 sont notées, et les deux archives d'origine sont conservées.

Je contrôlerais alors, dans cet ordre :

  1. serveur.ps1 : contrôle de chemin, ports, arrêt propre.
  2. app.mjs : sérialisation des ouvertures, reprise après échec, messages d'erreur.
  3. cheats.mjs et identity.test.mjs : lecture de rom_sha256, exclusion des empreintes mal formées ou contradictoires.
  4. store.mjs : rotation des copies miroir, sérialisation, comportement si IndexedDB échoue.
  5. hash.mjs et zip.mjs : mémoire, limites, taille annoncée contre taille réelle.
  6. player.html : création du fichier dans l'iframe, extension transmise au moteur.
  7. tests/ : ce que les tests vérifient vraiment, et ce que le moteur simulé masque.

Ordre conseillé

  1. Corriger MANDAT-CLAUDE-CODE.md et ETAT.md (rapide, sans risque).

  4. Corriger d'après les résultats, avec un test de régression par défaut trouvé.
  5. Seulement ensuite, décider de la fusion. Elle reste ta décision.
